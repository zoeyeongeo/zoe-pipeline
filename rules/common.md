# 공통 작업 규칙 (W)

### W-001 코드 변경은 흐름 안에서
- 심각도: MUST
- 규칙: 작은 변경은 /fix, 기능은 /feature 흐름을 따른다. /feature는 설계 게이트 승인 전에 구현하지 않는다. 스킬이 없는 동안(3단계 전)은 기능 작업 시 templates/spec.md · design.md로 Docs/features/<기능>/을 만들고 design.md 승인 후 구현한다. 승격 기준(새 파일, 공개 시그니처, SO·세이브 구조, 플레이 감각, 수정 파일 4개 이상) 중 하나라도 해당하면 기능 작업으로 본다
- 이유: 질문 품질과 무관하게 결과를 지키는 장치가 흐름 안에만 있다
- 강제: 문서 → (3단계) 스킬
- 예외: 사용자가 "그냥 고쳐"라고 명시한 한 줄 수정

### W-002 질문은 되돌리기 비싼 빈칸만, 최대 3개
- 심각도: SHOULD
- 규칙: 세이브 데이터 형식, 다른 시스템의 공개 API, 게임 규칙(기획 판단)은 질문한다. 수치·이름·내부 구조는 기본값(templates/defaults.md)으로 채운다
- 이유: 질문이 많으면 대충 던진 요청이 멈추고, 없으면 AI 기본값이 몰래 들어간다
- 강제: 문서 → 템플릿(spec.md 질문 칸)
- 예외: 없음

### W-003 가정은 드러낸다
- 심각도: MUST
- 규칙: 질문하지 않고 채운 빈칸은 "가정함"으로 표시하고 가정 목록(#, 항목, 값, 근거, 되돌리기 비용)에 남긴다
- 이유: 숨은 가정은 나중에 버그가 아니라 "원래 그런 것"처럼 보인다
- 강제: 템플릿(spec.md, design.md)
- 예외: 없음

### W-004 설계는 대안 2~3개 + 트레이드오프
- 심각도: SHOULD
- 규칙: /feature 설계 단계는 대안을 2개 이상 내고 추천안과 이유를 적는다
- 이유: 첫 아이디어로 굳는 것을 막는다
- 강제: 템플릿(design.md)
- 예외: /fix

### W-005 범위 밖 발견은 고치지 말고 등록
- 심각도: MUST
- 규칙: 작업 범위 밖에서 발견한 문제는 고치지 않고 TODO.md에 등록한 뒤 보고한다
- 이유: 영향 범위를 좁게 유지한다
- 강제: 문서 → (2단계) 범위 검사
- 예외: 범위 밖 문제 때문에 이번 작업이 컴파일되지 않을 때 — 멈추고 질문

### W-006 수정 파일 목록 밖 변경 금지
- 심각도: MUST
- 규칙: /feature는 design.md의 "수정 파일", /fix는 Explore의 영향 범위 밖 파일을 바꿔야 하면 멈추고 파일·이유를 보고한다. 승인되면 목록에 추가하고 계속한다
- 이유: 코드를 다 이해하지 못해도 범위를 벗어난 순간이 드러나게 한다
- 강제: 문서 → (2단계) Verify 범위 검사 (.meta, 자동 생성 파일 제외)
- 예외: 없음

### W-007 모드를 지킨다
- 심각도: MUST
- 규칙: 구현 단계 담당이 [나]이면 그 단계의 게임플레이 코드를 대신 쓰지 않는다. 담당 변경은 사용자 말("3번 AI가 해 줘")로만
- 이유: learn 모드의 목적(학습)과 지표(누가 짰는가)를 지킨다
- 강제: 문서 → (3단계) /feature 스킬
- 예외: 에셋 작업(SO 생성, 프리팹 조립, 인스펙터 연결)은 모드와 무관하게 AI (A 규칙)

### W-008 완료 주장 전에 증거
- 심각도: MUST
- 규칙: "완료/수정됨"이라고 말하기 전에 컴파일·테스트 결과를 실제로 확인하고 보여 준다. 확인 못 했으면 못 했다고 말한다
- 이유: 확인 안 된 완료가 가장 비싼 버그다
- 강제: 문서 → (2단계) 컴파일 hook
- 예외: 없음

### W-009 추측으로 단정하지 않는다
- 심각도: SHOULD
- 규칙: 확인하지 않은 동작·원인은 "확인 필요"로 따로 적는다. 디버깅은 guides/debugging.md 순서(증상 → 근거 → 가설 하나 → 하나씩 검증)
- 이유: 그럴듯한 추측이 고친 척을 만든다
- 강제: 문서, 리뷰 "확인 필요" 섹션
- 예외: 없음

### W-010 기록은 기능 단위로
- 심각도: SHOULD
- 규칙: 작업 기록은 Docs/features/<기능>/(spec.md · design.md · review.md)에 남긴다. 기존 대형 로그(Sequences.md, TASK.md)에는 추가하지 않는다
- 이유: 거대한 단일 로그는 매 세션 읽기 비용이 크다
- 강제: 문서 → (3단계) 스킬
- 예외: 없음

### W-011 출처 우선순위
- 심각도: SHOULD
- 규칙: 스타일·컨벤션은 zoe 규칙, 엔진 API 사실은 Unity 공식 플러그인 스킬을 따른다. 둘이 다르면 사용자에게 알린다
- 이유: 엔진 지식은 직접 만들지 않는다(설계 5장)
- 강제: 문서
- 예외: 없음
