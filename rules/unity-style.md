# Unity C# 코드 규칙 (C)

> 0.1.0 초안. `[RPG 이식]` 표시 항목은 모험가 RPG의 `Assets/Code/CLAUDE.md` 컨벤션으로 내용을 채워야 한다.
> 주석 원칙: 주석은 diff를 읽는 사람이 아니라 6개월 뒤 이 파일을 처음 여는 사람에게 쓴다. 변경 설명은 커밋 메시지와 review.md로.

### C-001 이름 규칙 [RPG 이식]
- 심각도: NIT
- 규칙: (RPG 컨벤션의 타입·메서드·필드·상수·이벤트 이름 규칙을 옮길 것)
- 이유: 읽기 쉬움
- 강제: 문서 → .editorconfig
- 예외: 외부 패키지 코드

### C-002 서식 [RPG 이식]
- 심각도: NIT
- 규칙: (중괄호, 들여쓰기, using 순서, 줄 길이를 옮길 것)
- 이유: diff 소음 감소
- 강제: 문서 → .editorconfig
- 예외: 자동 생성 코드

### C-003 유니티 클래스는 파일당 하나
- 심각도: MUST
- 규칙: MonoBehaviour/ScriptableObject 파일에는 해당 클래스와 그 중첩 클래스만 둔다. 파일명 = 클래스명
- 이유: 유니티는 파일명으로 스크립트를 연결한다. 어기면 컴포넌트가 Missing이 된다
- 강제: 문서 → (2단계) Analyzer ZOE003
- 예외: 없음

### C-004 구독과 해제는 짝으로
- 심각도: MUST
- 규칙: 이벤트·Bus 구독은 대칭 위치에서 해제한다 (OnEnable↔OnDisable, Awake/Start↔OnDestroy)
- 이유: 해제 누락은 파괴된 객체 호출, 중복 실행, 메모리 누수로 이어진다
- 강제: 문서 → 리뷰
- 예외: 정적 수명(앱 전체) 객체 — 이유를 주석 한 문장으로

### C-005 직렬화 필드 이름을 바꾸면 FormerlySerializedAs
- 심각도: MUST
- 규칙: [SerializeField] 또는 public 직렬화 필드 이름 변경 시 [FormerlySerializedAs("이전이름")]를 붙인다
- 이유: 없으면 씬·프리팹·SO에 저장된 값이 조용히 기본값으로 돌아간다
- 강제: 문서 → 리뷰
- 예외: 아직 어떤 에셋에도 저장된 적 없는 새 필드

### C-006 타입·인터페이스에는 summary
- 심각도: SHOULD
- 규칙: 클래스·구조체·인터페이스·열거형 선언에 /// <summary>로 책임을 한두 문장 적는다
- 이유: 타입의 책임은 코드만 봐서는 재해석 비용이 크다
- 강제: 문서 → (2단계) Analyzer
- 예외: private 중첩 타입

### C-007 구현부·override에는 summary를 달지 않는다
- 심각도: NIT
- 규칙: override 메서드, 인터페이스 구현 메서드에는 /// summary를 달지 않는다 (선언 쪽에 있다)
- 이유: 같은 설명이 두 곳에 있으면 한쪽이 낡는다
- 강제: 문서 → (2단계) Analyzer
- 예외: 구현이 선언과 다른 계약을 추가할 때

### C-008 메서드 안 주석은 "왜" 한 문장
- 심각도: SHOULD
- 규칙: 메서드 안 // 주석은 이상해 보이는 줄의 이유만, 한 문장으로. "무엇"을 되풀이하지 않는다. 판정: 지우면 코드만으로 알 수 없는 정보가 사라지는가?
- 이유: "무엇" 주석은 소음이고 코드와 어긋나기 쉽다
- 강제: 문서 → (2단계) Analyzer(두 문장 이상) + 리뷰("무엇" 판정)
- 예외: 없음

### C-009 주석에 변경 서술 금지
- 심각도: SHOULD
- 규칙: 주석에 "이제", "변경", "개선", "기존", "추가함", 번호 매긴 단계(// 1.)를 쓰지 않는다
- 이유: 변경 이력은 git이 안다. 6개월 뒤 독자에게는 의미가 없다
- 강제: 문서 → (2단계) Analyzer
- 예외: 없음

### C-010 주석에 도구 얘기 금지
- 심각도: NIT
- 규칙: 주석에 Claude, AI, 프롬프트, 세션 등 작성 도구 이야기를 쓰지 않는다
- 이유: 코드의 사실이 아니다
- 강제: 문서 → (2단계) Analyzer
- 예외: 없음

### C-011 Assert 메시지 형식 [RPG 이식]
- 심각도: SHOULD
- 규칙: (RPG의 Assert 메시지 형식을 옮길 것)
- 이유: 틀렸을 때 빨리, 어디서 틀렸는지 드러나게
- 강제: 문서 → (2단계) Analyzer
- 예외: 없음

### C-012 조정할 수치는 데이터로
- 심각도: SHOULD
- 규칙: 밸런스 수치(데미지, 쿨다운, 속도 등)는 하드코딩하지 않고 SO 또는 인스펙터 노출 필드로 뺀다
- 이유: 수치는 가장 자주 바뀌고, 바꿀 때 컴파일이 필요 없어야 한다
- 강제: 문서 → 리뷰
- 예외: 물리·수학 상수

### C-013 한 클래스 한 책임
- 심각도: SHOULD
- 규칙: 서로 다른 이유로 바뀌는 책임을 한 클래스에 모으지 않는다 (GOD class 금지). 다른 시스템에는 구체 클래스 대신 인터페이스/Bus로 의존한다
- 이유: 영향 범위를 좁게, 지우기 쉽게
- 강제: 리뷰
- 예외: 프로토타입 단계 — TODO.md에 분리 계획 등록
