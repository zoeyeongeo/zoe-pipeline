# Unity C# 코드 규칙 (C)

> 출처: 모험가 RPG `Assets/Code/CLAUDE.md` 코드 컨벤션·최적화 + `cs-review` 검토 항목 (0.3.0 이식).
> 새 코드는 따르고, 기존 코드를 일괄 수정하지는 않는다 — 파일을 건드릴 때 그 파일 안에서만 맞춘다.
> 주석 원칙: 주석은 diff를 읽는 사람이 아니라 6개월 뒤 이 파일을 처음 여는 사람에게 쓴다. 변경 설명은 커밋 메시지와 review.md로.

## 이름·서식

### C-001 이름 규칙
- 심각도: NIT
- 규칙:
  - 파일명 = 클래스명. 네임스페이스 = `Assets/` 아래 폴더 경로. 폴더는 복수형 (`Agents/`, `Modules/`), FSM은 `FSM/`
  - 접미어: ScriptableObject `*SO`, 추상 `Abstract*`, 인터페이스 `I*`, 열거형 `*Enum`. 이벤트 `On<사건>`, 받는 함수 `Handle<사건>`
  - private 필드 `_camelCase` — private·protected `const`, `static readonly`도 같음. `s_` 접두어 금지. public 상수는 PascalCase
  - `[SerializeField] private` 필드는 `camelCase` (밑줄 없음, C-016)
  - 프로퍼티·메서드·이벤트 PascalCase, 지역 변수·파라미터 camelCase, `bool`은 `Is`/`Can`/`Has`
- 이유: 이름만 보고 종류와 범위를 안다
- 강제: 문서 → .editorconfig, 리뷰
- 예외: 참조가 너무 많은 뼈대 타입은 프로젝트 CLAUDE.md에 예외로 적는다

### C-002 서식
- 심각도: NIT
- 규칙:
  - 블록 네임스페이스, 4칸 들여쓰기, Allman 중괄호
  - 한 줄 early return은 `if (x)` 다음 줄에 `return;`, 중괄호 생략. 그 외엔 중괄호
  - 한 줄 140자 이내. 넘으면 인자·연산자 앞에서 줄을 바꾸고 4칸 더 들이거나 위 줄 연산자에 맞춘다. 줄 끝 공백·탭 금지
  - 한 줄 반환은 표현식 본문(`=> ...`)을 다음 줄에
  - float 리터럴 `1f`, `-9.81f`. 기본값은 선언부에서 초기화
  - `using`은 `System.*` 먼저, 나머지 알파벳 순, 별칭은 맨 뒤 (Rider "Optimize imports" 기본값)
  - `.cs`는 CRLF / UTF-8. 줄바꿈을 LF로 바꾸는 도구(`sed -i` 등)로 편집하지 않는다
- 이유: diff 소음 감소
- 강제: 문서 → .editorconfig, (2단계) Analyzer
- 예외: 자동 생성 코드, 외부 패키지

### C-003 유니티 클래스는 파일당 하나
- 심각도: MUST
- 규칙: MonoBehaviour/ScriptableObject 파일에는 해당 클래스와 그 중첩 클래스만 둔다. 파일명 = 클래스명
- 이유: 유니티는 파일명으로 스크립트를 연결한다. 어기면 컴포넌트가 Missing이 된다
- 강제: 문서 → (2단계) Analyzer ZOE003
- 예외: 없음

### C-023 쓰지 않는 코드는 남기지 않는다
- 심각도: NIT
- 규칙: 쓰지 않는 `using`·필드·변수, 아무 일도 하지 않는 호출(빈 `base.X()` 등)은 지운다. 같은 계층의 다른 override와 호출 방식을 맞춘다
- 이유: 읽는 사람이 "왜 있지?"를 매번 추적하게 된다
- 강제: 문서 → 리뷰 → (2단계) Analyzer(안 쓰는 using)
- 예외: 부모 구현이 나중에 생길 것이 확정된 base 호출 — 이유를 주석 한 문장으로
- 출처: RPG 기준선 UNMAPPED 2건 (Y15 안 쓰는 using, Y10 빈 base 호출)

## 직렬화·이벤트

### C-004 구독과 해제는 짝으로
- 심각도: MUST
- 규칙: `+=` 한 곳마다 대칭 위치에 `-=` (Awake/Start/Initialize ↔ OnDestroy, OnEnable ↔ OnDisable). 구독 함수 쌍(`Subscribe`/`UnSubscribe`)도 같다
- 이유: 해제 누락은 파괴된 객체 호출, 중복 실행, 메모리 누수로 이어진다 (RPG 디버깅 "자주 나오는 원인" 1위)
- 강제: 문서 → 리뷰
- 예외: 앱 전체 수명 객체 — 이유를 주석 한 문장으로

### C-005 직렬화 이름을 바꾸면 FormerlySerializedAs
- 심각도: MUST
- 규칙: 직렬화 필드·프로퍼티 이름 변경 시 필드는 `[FormerlySerializedAs("옛이름")]`, 프로퍼티는 `[field: FormerlySerializedAs("옛이름")]`를 **윗줄에 따로** 단다
- 이유: 없으면 씬·프리팹·SO에 저장된 값이 조용히 기본값으로 돌아간다. 윗줄에 따로 두면 140자를 넘지 않고 나중에 떼기 쉽다
- 강제: 문서 → 리뷰
- 예외: 아직 어떤 에셋에도 저장된 적 없는 새 필드

### C-016 직렬화 노출 방식
- 심각도: SHOULD
- 규칙: 외부에 노출할 직렬화 값은 `[field: SerializeField] public X { get; private set; }`, 내부용은 `[SerializeField] private camelCase`. public 필드 금지. 그룹은 `[Header("...")]`
- 이유: 인스펙터 편집과 외부 쓰기 차단을 동시에
- 강제: 문서 → (2단계) Analyzer
- 예외: 에디터 코드가 백킹 필드에 접근하는 방법은 프로젝트 CLAUDE.md

### C-017 통지는 이벤트, 폴링 금지
- 심각도: SHOULD
- 규칙: 상태 변화는 `event` / `UnityEvent`로 알린다. 다른 객체 상태를 매 프레임 확인하지 않는다
- 이유: 폴링은 결합도와 프레임 비용을 함께 올린다
- 강제: 리뷰
- 예외: 연속값(입력 축, 거리 등)

## 주석

### C-006 타입에는 summary
- 심각도: SHOULD
- 규칙: 클래스·구조체·인터페이스·열거형에 여러 줄 `/// <summary>`, 한두 문장. 첫 문장은 "~하는 클래스/모듈/인터페이스/열거형입니다." 속성(`[...]`)보다 위에. 인터페이스 멤버와 인터페이스에 없는 public 메서드는 한 줄 `/// <summary> ~합니다. </summary>`, 프로퍼티는 명사구. 매개변수 뜻이 이름만으로 안 보이면 `<param>`·`<returns>`
- 이유: 타입의 책임은 코드만 봐서는 재해석 비용이 크다
- 강제: 문서 → (2단계) Analyzer
- 예외: private 중첩 타입

### C-007 구현 쪽에는 summary를 달지 않는다
- 심각도: NIT
- 규칙: 인터페이스(직접 만든 것·Input System·`IPointerDownHandler`·`IDisposable` 등)에 있는 멤버의 구현, `override`, Unity 메시지(`Awake`, `Update` …)에는 summary를 달지 않는다
- 이유: 같은 설명이 두 곳에 있으면 한쪽이 낡는다
- 강제: 문서 → (2단계) Analyzer
- 예외: 구현이 선언과 다른 계약을 추가할 때

### C-008 메서드 안 주석은 "왜" 한 문장
- 심각도: SHOULD
- 규칙: 메서드 안 `// `는 이상해 보이는 줄의 이유만, "-다"로 끝나는 한 문장. 덧붙일 이유는 "~므로"·괄호로. "무엇"은 쓰지 않는다. 판정: 지우면 코드만으로 알 수 없는 정보가 사라지는가?
- 이유: "무엇" 주석은 소음이고 코드와 어긋나기 쉽다
- 강제: 문서 → (2단계) Analyzer(두 문장 이상) + 리뷰("무엇" 판정)
- 예외: 없음

### C-014 주석 언어와 필드 주석
- 심각도: NIT
- 규칙: 주석은 한국어. 필드·직렬화 프로퍼티·이벤트는 줄 끝 `// 명사구`, 열 맞춤, 마침표 없음. 이름만으로 뜻이 보이는 모듈·컴포넌트 접근 프로퍼티는 생략
- 이유: 한 프로젝트 안에서 주석 형식이 섞이지 않게
- 강제: 문서 → 리뷰
- 예외: 외부 패키지에서 가져와 고쳐 쓰는 코드의 기존 영어 주석

### C-009 주석에 변경 서술 금지
- 심각도: SHOULD
- 규칙: 주석에 "이제", "변경", "개선", "기존", "추가함", 번호 매긴 단계(`// 1.`)를 쓰지 않는다
- 이유: 변경 이력은 git이 안다. 6개월 뒤 독자에게는 의미가 없다
- 강제: 문서 → (2단계) Analyzer
- 예외: 없음

### C-010 주석에 도구 얘기 금지
- 심각도: NIT
- 규칙: 주석에 Claude, AI, 프롬프트, 세션 등 작성 도구 이야기를 쓰지 않는다
- 이유: 코드의 사실이 아니다
- 강제: 문서 → (2단계) Analyzer
- 예외: 없음

### C-021 주석이 말하는 동작은 코드에 있어야 한다
- 심각도: SHOULD
- 규칙: 새로 쓴 주석도, 기존 주석도 summary · 위 줄 `//` 주석이 말하는 동작(호출, 조건, 순서, 보장)이 실제 코드에 있는지 확인한다. 메서드·클래스의 동작이나 책임을 바꾸면 그 summary, 위 줄 `//` 주석, 짝을 이루는 선언(인터페이스·델리게이트·이벤트)의 주석을 같은 변경에서 다시 읽고 고친다. 코드에 없는 동작을 말하거나 코드와 반대말을 하는 주석은 고치거나 지운다
- 이유: 낡은 주석은 없는 주석보다 나쁘다. 읽는 사람이 코드 대신 주석을 믿는다. 새로 쓴 주석도 코드가 하지 않는 일을 약속할 수 있다
- 강제: 문서 → 리뷰
- 예외: 없음
- 출처: RPG 기준선 UNMAPPED 4건 (3번 장착 ×2, 5번 드랍, Y10), intake 2026-11-25 (새로 쓴 주석)

## 검증·로그

### C-011 Assert·로그 메시지 형식
- 심각도: SHOULD
- 규칙:
  - 필수 의존성은 `Debug.Assert`로 확인한다. 형식은 `Assert`·`LogWarning`·`LogError` 공통: 한국어 `$"[클래스명] 무엇이 어떻다: 대상"` + 마지막 인자로 context 오브젝트(`this`). 대상은 MonoBehaviour면 `{gameObject.name}`, SO면 `{name}`. 오브젝트가 없을 때(static)만 context를 뺀다
  - 문구는 넷 중 하나: `x 연결 안 됨`(인스펙터 칸이 빔) · `IFoo 모듈 없음` / `Foo 컴포넌트 없음`(조회 결과 null) · `x 중복` · `x 찾지 못함`. 결과는 `→ 이동하지 않음`처럼 뒤에, 값(인덱스·슬롯·경로)은 괄호로
  - **Assert 하나에 조건 하나** (`&&`로 묶지 않는다)
  - 예: `Debug.Assert(_renderer != null, $"[ComboAttack] IRenderer 모듈 없음: {gameObject.name}", this);`
- 이유: 틀렸을 때 콘솔에서 무엇이, 어디서 틀렸는지 바로 드러나고 눌러서 이동할 수 있다
- 강제: 문서 → (2단계) Analyzer(조건 개수, 접두어 형식)
- 예외: 없음

### C-015 로그 수준과 디버깅 로그
- 심각도: SHOULD
- 규칙: `Assert`는 개발 중 연결 실수, `LogWarning`은 에셋 검증·복구된 문제, `LogError`는 진행할 수 없는 문제. 디버깅용 `Debug.Log`는 남기지 않는다 (상시 디버그 도구는 별도 폴더)
- 이유: 콘솔 소음이 진짜 경고를 묻는다
- 강제: 문서 → (2단계) Analyzer(`Debug.Log` 호출)
- 예외: 없음

### C-022 초기화가 실패해도 정리 경로는 터지지 않는다
- 심각도: SHOULD
- 규칙: 초기화(`OnStart`·`Initialize`·`Start`)에서 받는 참조는 실패하거나 아직 불리지 않았을 수 있다. 그 뒤에 항상 불리는 경로(`OnEnd`·`OnDestroy`·`OnDisable`·구독 해제)와, 실행 중 사라질 수 있는 대상(타깃·외부 오브젝트)을 매 프레임 쓰는 경로는 null을 확인한 뒤 쓴다(`?.`, early return)
- 이유: 정리 경로의 NullReferenceException은 원래 원인(초기화 실패)을 가리고, 해제를 중간에 끊어 C-004 누수를 만든다
- 강제: 문서 → 리뷰
- 예외: 필수 의존성 자체의 누락은 C-011 Assert로 잡는다 (이 규칙은 그 뒤에도 터지지 않게 하는 것)
- 출처: RPG 기준선 UNMAPPED 4건 (추적 OnEnd·OnUpdate, 6번 줍기 OnDestroy, Y14 OnDestroy)

## 성능

### C-018 프레임 함수에서 조회 금지
- 심각도: SHOULD
- 규칙: `Update`/`FixedUpdate`/`LateUpdate`에서 `GetComponent`, `GetModule`, `Find*`, `Camera.main`을 호출하지 않는다. 초기화에서 한 번 캐싱
- 이유: 매 프레임 비용, 그리고 null 원인 추적이 어려워진다
- 강제: 문서 → (2단계) Analyzer
- 예외: 없음

### C-019 매 프레임 할당 금지
- 심각도: SHOULD
- 규칙: 프레임 함수에서 `new`, LINQ, 문자열 결합 금지. 컬렉션은 재사용
- 이유: GC 스파이크
- 강제: 리뷰
- 예외: 이벤트성으로 드물게 실행되는 경로

### C-020 프레임 함수 위치
- 심각도: SHOULD
- 규칙: 물리 이동은 `FixedUpdate`, 입력·FSM 갱신은 `Update`. 쓰지 않는 `Update`는 두지 않는다. 애니메이터 파라미터·상태는 문자열 대신 해시
- 이유: 물리 떨림·입력 누락 방지, 빈 메시지도 호출 비용, 문자열 오타는 조용히 실패한다
- 강제: 리뷰 → (2단계) Analyzer(빈 Update, 문자열 애니메이터 접근)
- 예외: 없음

## 설계

### C-012 조정할 수치는 데이터로
- 심각도: SHOULD
- 규칙: 밸런스 수치(데미지, 쿨다운, 속도 등)는 하드코딩하지 않고 SO 또는 인스펙터 노출 필드로 뺀다
- 이유: 수치는 가장 자주 바뀌고, 바꿀 때 컴파일이 필요 없어야 한다
- 강제: 문서 → 리뷰
- 예외: 물리·수학 상수

### C-013 한 클래스 한 책임, 인터페이스 의존
- 심각도: SHOULD
- 규칙: 서로 다른 이유로 바뀌는 책임을 한 클래스에 모으지 않는다 (GOD class 금지). 다른 시스템에는 구체 클래스 대신 인터페이스로 의존한다. 부득이하게 구체 타입에 의존하면 이유를 말한다
- 이유: 영향 범위를 좁게, 지우기 쉽게
- 강제: 리뷰
- 예외: 프로토타입 단계 — TODO.md에 분리 계획 등록
